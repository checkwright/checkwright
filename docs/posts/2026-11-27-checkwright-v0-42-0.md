# Checkwright v0.42.0

*2026-11-27*

Checkwright catches reproducible classes of unsupported claims in coding-agent delivery before merge, and this release gives every platform archive on a Release its own `.sha256` sidecar and a build attestation, so a binary-only consumer can check an archive before extracting it. It also reads a turbofish holding a fn-pointer arrow as a call, and holds a source build's release stamp to the grammar `--verdict-lookup` reads.

- Each platform archive now ships with its own `.sha256` and is covered by a build attestation, and the Release job verifies every asset's attestation before the Release exists.
- `check-exec-write` now reds a write or exec call whose turbofish type argument holds a fn-pointer arrow.
- A source build refuses a `CHECKWRIGHT_BUILD_VERSION` outside the version grammar instead of stamping keys `--verdict-lookup` refuses.

## New and tightened gates

- `check-exec-write` — reads a turbofish call whose type argument holds a fn-pointer arrow, where `std::fs::copy::<fn() -> ()>(a, b)` read as no call and passed: such a site now reds like its plain spelling; move it into a helper, as for any other site. A `fn(…)` pointer type is no longer read as a call to `fn`.

## Behavior changes

- **The platform archives' sidecars and attestation** — each `checkwright-gates-<version>-<target>.tar.gz` on a Release now carries its own `.sha256` beside it, and every Release asset other than a sidecar is the subject of a build attestation: the tarball's unchanged, the archives and the companion archive in a second. The `release` job verifies every asset's attestation before the Release exists. Nothing to do; a binary-only consumer can now check an archive before extracting it, with `sha256sum -c` against its sidecar and `gh attestation verify <archive> --repo checkwright/checkwright --source-ref refs/tags/v<version>`.
- **The release stamp's grammar** — a binary built from source now refuses a `CHECKWRIGHT_BUILD_VERSION` holding anything but ASCII letters, digits, `.`, `+` and `-` after a leading `v`, naming the value, where it used to stamp it and print `--verdict-key` keys that `--verdict-lookup` refused. A `git describe` answer outside that grammar now leaves the stamp empty. Nothing to do for a released binary; a source build setting such a version sets one in the grammar.

## Upgrading

Replace the vendored kit directories wholesale at `v0.42.0`, or run `checkwright update`. Regenerate your generated artifacts; each freshness gate that reds prints its own regen command. Then run the full battery.

**The allowed red.** `check-exec-write` may red on a write or exec call whose turbofish type argument holds a fn-pointer arrow; move the site into a helper, as for its plain spelling.

The behavior changes above are declared for reading, not a mechanical scan. If a gate reds that this note does not name, the upgrade smoke was supposed to catch it first — [open an issue](https://github.com/checkwright/checkwright/issues), because that is a defect in the release rather than work for you.
