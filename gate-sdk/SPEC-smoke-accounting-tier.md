# SPEC amendment: smoke-accounting-tier

The precommit `check-install-disposition` holds smoke registration for `zero-config`
gates only. The full accounting, where every shipped gate is registered, probed
exempt or hand-declared, runs in `--run-consumer-smoke` at validate. So an
unregistered `on-surface` gate was caught one stage late, twice. The entry asked
which tier should hold the full accounting. **This amendment rules that validate
keeps it. The accounting is a probe, not a static read, so no precommit member can
hold it. The two costs the entry names are closed where they arise: the landing
session runs the accounting before it commits, and the validate red names its own
remedy.**

**The measurement the ruling rests on (2026-09-21).**

- **The accounting is not separable from running the smoke.** A full
  `--run-consumer-smoke` run prints
  `accounting — 13 unregistered gate(s) probed in 110ms (10 self-declared, 3 hand-declared, 0 unaccounted)`.
  The verdict branches on each unregistered gate's exit code *in the scratch
  consumer* (§Consumer smoke, the registration accounting). Of the 13, 10 are exempt
  by probe and carry no written reason by design. The section refuses to demand one:
  a reason written where none is owed is the beginning of a maintained roster.
- **So a static widening reds ten gates today.** Widening assertion B to "registered
  or `# smoke-unregistered:`-declared" for every disposition would red those ten.
  Their only escape would be the declarations the design forbids. Only three
  `# smoke-unregistered:` lines exist in the tree
  (`grep -n "smoke-unregistered:" */smoke/install.sh`).
- **Moving the probe to precommit costs the whole smoke.** The full run takes 49 s
  of wall-clock, against a battery of about 41 s. The probe needs the scratch
  consumer the run builds, and caching its verdict across runs is refused on
  §Consumer smoke's own ground.
- **Both attested instances were one-line registrations** (`1e18d154`, `d0b496fa`),
  and the second one's registrar was a different kit from the shipping one. The
  probe classified both correctly. What they cost was latency and misattribution.
  The batch session read a registration omission as its own gate misbehaving.

## What changes

### (1) The session landing a shipped gate runs the accounting before its commit {mechanical}

**Not yet applied.** §Consumer smoke's registration-accounting text gains the landing
obligation. The session that adds a kit-shipped gate, or changes one's `# install:`
disposition, runs `--run-consumer-smoke` before the commit that lands it and repairs
any unaccounted line in that commit. The cost is one run, about 49 s, per gate
landing. Every other commit stays exempt, which is what keeps it proportionate.
§check-install-disposition assertion B gains one sentence: the non-`zero-config`
half is held there, at landing and at validate, because its verdict is a probe
result.

**The honest limit, in the section.** The obligation is prose. A landing session that
skips it is caught at validate, exactly as today, but now with the remedy in hand
(delta 2).

### (2) An unaccounted line names its remedy {mechanical}

**Not yet applied.** In `native/src/emit/run_consumer_smoke.rs`, each `unaccounted:`
line gains a `help:` continuation. It tells the reader to register the gate in the
`smoke/install.sh` of the kit that seeds the gate's subject surface, which need not
be the shipping kit. Otherwise it points to the shipping kit's `smoke/install.sh`
and the `# smoke-unregistered: <gate> — <reason>` declaration, for a vacuous pass. The
three-count clean line and the verdict are unchanged. The reader is the validate
session, and the build session that owns the defect.

## Producers and consumers

- **The landing obligation (delta 1).** Producer: the session landing the gate.
  Consumers: the landing commit, and the validate `consumer_smoke` suite that
  backstops it. No name is minted.
- **The help line (delta 2).** Producer: the accounting phase, reached on every
  `--run-consumer-smoke` run. Consumer: whoever reads a red run. It is a new line on
  the existing channel, so no field is added to the success token.
- **Point 5.** Nothing narrows.
