# SPEC amendment: steered-fixture-roots

Queue entry: `steered-fixture-walk-roots-unverified`, selected for `couples-field-semantics` as its
steered-walk unit (operator direction, 2026-09-15, lead-relayed); its own delta, a design call per
member. It is independent of the couples-semantics amendments and may land in any order.

## The question, and what this stage probed

Unit test A (gate-sdk/SPEC.md §check-reads-couples) holds a member's declared walk roots to what its
fixture cases observe. Three freshness members pass two positionals in **every** `good/` and `bad/`
case: the committed projection and a pre-baked emission. Those positionals steer the gate off its
emitter, so no case reaches a walk and A holds each declaration over nothing.
§check-reads-couples states that limit ("unit test A observes no walk to hold their `?` to"). The
entry asks for a default-branch case per member, plus `check-footprint-fresh`'s missing root.

**Probed at this stage.**

- **The fixture case set is closed.** `walk::fixture_case_dirs` returns exactly `good/` and `bad/`
  under `<kit>/gate-tests/<gate>/`. A third, default-branch case directory would be invisible to A and
  to the fixture-pair contract alike. So the default branch **re-purposes one of the pair** and adds
  no case. Minting a case kind is a gate-sdk contract change this unit does not own.
- **`check-footprint-fresh`'s empty root set is a false no-walk claim, in two walks.**
  `emit/footprint.rs:31` is `walk::glob_files(".", ["*/SPEC.md"])`, a static root with a
  crate-literal filter. `:90` is `glob_files(<kit>, ["templates/**/*.md"])`, rooted at each kit that
  `:31` found, so no literal names it.
- **`check-value-rollup-fresh` walks more than it declares.** `emit/value_rollup.rs:35-36` calls both
  `enforcement_map::measure()` and `footprint::measure()`, so its emitter reaches footprint's two
  walks as well as the `GATE_SDK_ENFORCE_SCAN_DIR` walk its one `?` names. Its descriptor already
  couples `native/src/emit/footprint.rs`, which is how the reach shows.
- **Unit test C cannot see these.** Its property test reads `src/gates/<name>.rs` alone, and every walk
  here lives in an `emit/` module. That is the honest limit §check-reads-couples already gives C (*a
  module may fall outside them*), and why only an observing case closes it.
- **Declaring `:31`'s root exposes an under-couple.** Neither `check-footprint-fresh`'s couples nor
  `check-value-rollup-fresh`'s names a kit `SPEC.md`, yet a kit's `SPEC.md` appearing or leaving
  changes the kit list both emitters derive.

## The seam

Kit mechanism only: registry declarations, fixture cases and descriptor couples. No knob and no
private rule content. The fixture corpora are synthetic, never a copy of this repo's kits.

## What changes

### (1) Each member's `good/` case takes the default branch {design-bearing}

`context-kit/gate-tests/check-footprint-fresh/good/`, `gate-sdk/gate-tests/check-enforcement-fresh/good/`
and `scripts/gate-tests/check-value-rollup-fresh/good/`. Each case changes in four ways:

- It drops its `args`, `emit.txt` and `projection.txt`.
- It stages a minimal synthetic corpus the member's emitter reads from the case directory. The
  corpus is **one kit** directory carrying a `SPEC.md` and a `templates/` markdown file, plus
  whatever each emitter's other inputs need.
- Those inputs come through **case-local knob files** at the case's `<gates-dir>`. The child reads
  them from its working directory (§lib/gate.sh), never from this repo's tree. Where the inputs
  include a command, such as `EVIDENCE_KIT_SUITES`' runners, the case resolves that knob empty rather
  than spawning a program.
- It commits the projection at the member's default path, generated by running the member's own
  emitter inside the case.

`expect.txt` stays the clean line. `bad/` keeps its positionals: the steered stale-projection case
is the cheap hermetic statement of the red half, and the pair then covers both branches.

**One kit, deliberately.** The footprint walk at `:90` observes one root per kit, and each `?`
absorbs exactly one observed root. A one-kit corpus makes the arity statement exact. Its limit, that a
per-kit loop is held to one iteration, is stated beside the declaration in delta 2's comment rather
than discovered.

**A member that cannot be staged hermetically stops the batch.** If an emitter reaches state no
case-local knob can redirect, such as a `git` query against the enclosing repository, build does not
fall back to keeping the positionals. It escalates: the unit's envelope is an observing case, and a
steered case under a new name is the same gap.

### (2) The declarations follow what the cases observe {design-bearing}

`native/src/gates/mod.rs`:

- **`check-footprint-fresh`**: `&[]` becomes
  - `(".", "glob:lit:*/SPEC.md", "", "")`
  - `("?", "", "", "dynamic@src/emit/footprint.rs:90 via emit::footprint::emit")`
- **`check-value-rollup-fresh`** keeps its `enforcement_map.rs:336` `?` and gains
  - `(".", "glob:lit:*/SPEC.md", "", "")`
  - `("?", "", "", "dynamic@src/emit/footprint.rs:90 via emit::value_rollup::emit")`
- **`check-enforcement-fresh`** is unchanged unless its default case observes a root it does not
  declare.

Each `via` clause is what the locator assertion holds. If a clause names the wrong first hop, the
assertion reds, and its correction is calibration. Each member's registry comment gains one line
binding the one-kit arity limit (delta 1). The authoritative outcome is unit test A over the new
`good/` cases: a root A observes and no declaration carries is added, whatever this delta
predicted. The `--needs` half of test A runs over the same cases, so an undeclared spawn on the
default branch reds there too, and is declared the same way.

gate-sdk/SPEC.md §check-reads-couples, the paragraph **What it decides is presence and placement**.
**Not yet applied:** *where a member's only fixture case steers it off the walk through a positional —
`check-enforcement-fresh` and `check-value-rollup-fresh`, whose emitter walk is rooted at a scan knob —
the clause records the chain rather than proving it, and unit test A observes no walk to hold their
`?` to either* becomes *where a member's walk lives off its module, the clause records the chain
rather than proving it; what holds the declaration is a fixture case taking the walk, which is why a
freshness member whose `bad/` case steers through positionals keeps a `good/` case on its emitter's
default branch*.

### (3) The couples the new roots demand {mechanical}

`context-kit/checks/check-footprint-fresh.gate` and `scripts/check-value-rollup-fresh.gate` each gain
`*/SPEC.md`, the covering token for delta 2's `.` root. `check-reads-couples` reds on this tree
without it (a kit's `SPEC.md` is read and uncovered), so it lands in the same commit as delta 2. The
generated hook and the coupling-graph artifact are regenerated.

## Producers and consumers

- **The default-branch cases (delta 1).**
  - **Producer:** the fixture tree.
  - **Consumers:**
    - `--run-gate-tests`, which reads the clean line.
    - Unit test A's walk half, which reads observed roots and declared prunes.
    - Unit test A's spawn half (`--needs`).
    - `walk::fixture_case_dirs`, which already enumerates `good/`.
  - **Enabling configuration:** the case-local knob files, which the child reads from its working
    directory on every run.
- **The declarations (delta 2).**
  - **Producer:** the registry tuple.
  - **Consumers:**
    - `--reads`.
    - `check-reads-couples`, which asserts the new `.` roots' coverage on this tree and skips-and-counts
      the new `?` roots.
    - `--emit reads-census`, which prints `check-footprint-fresh` for the first time and grows
      `check-value-rollup-fresh`'s line.
    - The locator assertion, which gains two sites.
- **Readers' red conditions (point 5).** Delta 1 removes the positional cases from `good/`, which
  narrows what `good/` asserts about the steered branch. What reds:
  - `--run-gate-tests` reds if the emitter's output inside the case differs from the committed
    projection. That is the freshness assertion running for real. Regenerate inside the case.
  - Unit test A reds on any undeclared observed root or spawn. Delta 2 exists to answer it.
  - `check-reads-couples` reds on delta 2's `.` root until delta 3's couple lands.
  - The census and the locator site count change. Neither asserts a number.
  - The steered branch keeps its red statement in `bad/`, and no reader counts cases.
