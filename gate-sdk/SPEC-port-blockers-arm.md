# SPEC amendment: port-blockers as a bridged-arm table member

The port oracle — the instrument whose `--tree` owed count *is* the completion
predicate TRAJECTORY.md §PRIORITY DIRECTIVE — the port track's sequence states —
is itself still shell. `gate-sdk/bin/port-blockers.sh` becomes a bridged-arm
table member of the binary and leaves the tree, taking the last `# port-until:`
declaration with it. The route was ruled at gate-sdk/SPEC.md §The non-gate arm
and deliberately left unminted; this amendment mints it.

**The frame.** The contract composer ruled at `native-gate-port-remaining-corpus`
on 2026-08-28 — *the owed files behind one specification section, ported behind
the one amendment that section needs* — is the shape this unit takes: the
section is gate-sdk/SPEC.md §port-blockers and the file set behind it is a
singleton, because that section governs exactly one file. It is **not** a cut of
that entry's remaining corpus and does not displace the drift-kit cut that entry
names first, which stays held on the operator question. This is a distinct entry
whose route was ruled separately, and it fits the composer's shape rather than
consuming its sequence.

**No decomposition is available and that is a finding, not a preference.** The
held row clears only when the file leaves the tree, so porting one arm and
leaving two would move nothing on the predicate. Nor may the port leave a thin
shell front-end behind it: `--run`'s front-end `bin/run-gates.sh` is itself
still shell and still owed, so a `bin/port-blockers.sh` reduced to a front-end
would be the same file in the same corpus. The arm is therefore reached through
the front-end that already exists.

**What this amendment does not depend on.**
`port-completion-predicate-contributor-side-accounting` is open and
operator-class, and nothing here turns on its answer: this file is in neither
of that question's readings — its disposition was ruled separately — and the
port moves *held* 1 to 0 while leaving *owed* at 141 under either reading.
Delta 9 rewrites `gate-sdk/smoke/install.sh`, which is inside that question's
disputed 33, but rewriting a file changes neither its disposition nor its
membership in the set.

**The seam, ruled.** Everything in deltas 1 through 10 is **kit mechanism**: an
arm, a knob roster, a sentinel, a corpus rule, a tokenizer and a report format,
none of which names a project's directories, vocabulary or work queue. The
`# no-port:` cause and the `# port-until:` slug the arm reads stay **consumer
content** by construction, exactly as the fields already rule. The one file that
stays shell stays shell *because* of the seam: the measured-claim emitter is the
value of a consumer knob, sits in a directory the payload assembler never packs,
and carries this project's claim vocabulary — porting it would ship that
vocabulary in every adopter's binary. No knob is minted for either payload and
none for the builtin classification, which is a property of the interpreter
rather than a consumer's to configure.

**One coupling the port removes and may not replace, ruled rather than left to
be met at build.** The consumer claim gate's `couples=` reaches this tool today
through its kit-root shell glob, so an edit to the tool re-runs the gate whose
value it feeds. After the port the implementation is crate source, which that
field does not reach — and it must **not** be widened to reach it, because that
descriptor is a canon-kit descriptor and naming this project's crate directory
in a kit literal publishes this project's layout. The gap is recorded and left
covered by the full-battery-before-every-commit rule, which is exactly the
disposition §port-blockers already takes for the consumer-defined corpus its own
uncovered set sits in.

## What changes

### (1) `--emit-port-blockers`, and the argv grammar the three arms become

The arm's flag spelling is minted here, with its callers, as
`--emit-port-blockers`. {design-bearing}

It is an `Arm::Emit` member of the bridged-arm table, and the variant is forced
rather than chosen: that variant's contract — a rendered document to stdout at
exit 0, a message on stderr at exit 2 — is the whole of the shell tool's own
exit behaviour, covering the help arm, the unrecognized-argument refusal, the
non-repository refusal, the missing-registry refusal and the
unresolvable-member refusal with nothing left over. Because it is `Arm::Emit`
it does not inherit the dispatch union `Arm::Run` carries, which is correct: it
dispatches nothing.

The `--emit-` prefix is not a third stretch of the word. §The non-gate arm
demoted `--emit-` from a family name to a per-arm spelling, and the two members
that strained it — a mode answering two integers, and a runner returning a
verdict — strained it because they render no document. All three of this arm's
modes render a roster. The prefix also carries the reachability: the only
front-end that resolves a bridged arm's environment is
`bin/run-gates.sh --emit <name>`, which composes the flag as `--emit-<name>`,
so a differently-spelled arm would be reachable by no shipped caller at all.

The three arms become the arm's own argv, unchanged in spelling: no argument
answers criterion 7, `--group` answers criterion 6, `--tree` answers the
completion predicate. They pass §The non-gate arm's distinguishing test as
arguments the rule itself consumes rather than arguments redirecting resolved
config, so nothing is deleted. `-h` / `--help` as the first argument prints
usage on stdout at exit 0 **whatever follows it** — the shell tool's
help-before-arity ordering is not a defect to repair but exactly what §The
`bin/`-tool contract states, and a port that refused help-plus-extra would be a
silent behaviour change on a case that contract already decides. An
unrecognized argument is usage on stderr at exit 2. The usage text carries every
arm and keeps the clause a governed surface quotes back at it — that a registry
arm reading zero *says nothing about the tree*.

The documented invocations become
`bash gate-sdk/bin/run-gates.sh --emit port-blockers [--gates-dir <dir>] [--group | --tree]`.

### (2) The declared knob roster, and the registry-scoped union sentinel

The arm declares its own structural knobs and one union sentinel, because the
knob names it must resolve are not knowable when a static roster is
written. {design-bearing}

Its own knobs are the four §The non-gate arm already names — the gates dir, the
kit roots, the resolved prune set and `GATE_SDK_PROGRAM_FLOOR` — plus the
fixture-dirs root criterion 2 reads through. That roster is what forces the
family: a hardcoded top-level flag receives no configuration at all, so this
tool ported as one would resolve platform defaults and ignore every consumer
override.

**The fifth read §The non-gate arm's recorded route does not account for.**
The shell tool resolves an *arbitrary* knob's default — one discovered at scan
time from a command-position expansion, or handed back by a `--needs` row's
`?<TAB><knob>` line — through the bridge resolver. A bridged arm receives only
its declared knobs and the bridge refuses an undeclared read, so a fixed roster
cannot answer, and the three fallbacks are each refused: reporting `?` for
every expansion loses rows the tool resolves today, parsing kit config inside
the crate is a second definition of the one resolver, and re-entering the shell
library from the compiled arm is the thing the port exists to end.

The mechanism is the union sentinel the crate already ships for exactly this
shape — the one `check-reads-couples` declares when its knob names are not known
until run time — minted here as a second member of that class whose expansion is
the union of every knob every member of the **tree's** registry declares. The
scope is the tree's registry and not the crate's, for the correctness
requirement §The non-gate arm states for `--run`: a crate-wide union asks the
bridge to resolve a knob whose owning kit is not vendored, which is the
does-not-define refusal, fail-closed, on an adopter's first battery.

**The union is provably sufficient, which is why no wider set is minted.** A
command-position expansion naming a knob its own member does not declare already
fails the bridge's undeclared-knob refusal at that member's own dispatch, so
every knob this arm can ever resolve is one some registered member declares. A
knob outside the union is reported `?` with the same *default unresolvable*
evidence the shell tool prints — the fail-safe direction unchanged.

**The effective gates dir crosses as an explicit argument**, exactly as `--run`'s
does and for the same reason: the sentinel expands before the bridge is built,
so the registry that scopes it can only arrive as argv. Absent it the union
degrades to the arm's own knobs and expansions report `?` — an under-report, the
direction the tool already fails in, never a fail-open. `--tree` needs no gates
dir and takes none, so the one arm a machine reads and a session runs most keeps
the short spelling. Two alternatives are refused: widening
`bin/run-gates.sh --emit` to resolve and pass a gates dir unconditionally would
present an argument every one of the nine existing emit arms refuses, and
bridging the structural knobs ahead of the roster request is a change to shared
bridge mechanism whose blast radius is every member. The build may take the
front-end route only if it can do so without moving any existing arm's argv
contract.

### (3) The `--tree` arm on the shared corpus rule, with a refusal that rule does not carry

`--tree` is built on the crate's existing tracked-shell-tree corpus rule rather
than on a second copy, and adds its own repository probe ahead of it. {mechanical}

The compiled corpus rule already computes what the shell arm computes — tracked
`*.sh`, less the `*.test.sh` suffix, less the resolved prune set — and
§check-gate-exemption-tasks' tree arm has called it since that arm landed, so
the derivation is shared rather than duplicated.

**It diverges in exactly one place and the divergence must be absorbed by the
arm, never by the shared rule.** Where git cannot answer, the shared rule
degrades to an empty corpus; `--tree` refuses with exit 2, because its whole
subject is the tracked tree and a silently empty corpus would print `0 owed` —
the completion predicate — where the shell tool refuses. §check-gate-exemption-tasks
states the opposite disposition for itself, deliberately and on a monotonicity
ground, so "fixing" the shared rule would break its other reader. The arm probes
for a repository and refuses before it calls.

The arm dispatches ahead of registry resolution, so a tree carrying no
`gates.list` still answers for its own shell. The front-end path preserves this:
`bin/run-gates.sh`'s `--emit` branch execs before it touches the registry.

### (4) The header-block read promoted, and the disposition triple minted beside it

The private header-block reader moves to a shared home and gains the
well-formedness rule that turns a header block into a disposition. {mechanical}

The reader — the leading run of shebang, comment and blank lines — exists today
inside the one gate module that needed it first, with a single call site. It
moves to a universal layer beside the corpus rule it is the other half of; that
layer takes no `.gate` descriptor coupling, on the ground already stated for the
universal layers.

The disposition triple exists nowhere and is minted with both its readers: from
a file's header block, `no-port` when exactly one `# no-port:` line carries a
non-empty cause, `port-until:<slug>` when exactly one `# port-until:` line
carries a slug, and `owed` otherwise — an empty cause, a missing slug, and a
file carrying both are one rule rather than three, because a file that has not
made a reviewable declaration has not made one, and `owed` is the over-count
direction absence already takes. Its readers are this arm and the exemption
gate's tree half, which today inlines a narrower scan that skips a bare field
rather than scoring it.

### (5) The command-position tokenizer, compiled

The bash command-position scanner the two registry arms are built on is written
in the crate; nothing of the kind exists there today. {design-bearing}

This is the port's cost centre and its risk: roughly a hundred and eighty lines
of dense awk — a character state machine over quoting, command-substitution
frames, heredocs, here-strings, double-bracket state, `case` levels, arithmetic
and array-literal skipping, and backslash continuation — with no counterpart
anywhere in the crate. The nearest thing the crate has is a single-line byte
scan with no quoting state at all, and it is not a starting point.

**Two tokenizer rules are repairs, not conveniences, and the port carries them
forward by name**: a here-string is consumed whole as a single redirection
operator ahead of the heredoc branch, so an operator consumed whole cannot be
re-entered part-way; and a `)` pops a pushed substitution frame ahead of any
case-pattern reading **only inside double brackets**, the unscoped form having
been tried and caught stealing a genuine `case` pattern's frame. Both were found
by execution after the scan was caught abandoning declarations part-way and
reporting the unread remainder as clean.

**The two derived negative inputs part company under compilation, and only one
of them is interpretive.** The function-name harvests — a kit library's
definitions, a declaration's own definitions, and the names a declaration probes
with `declare -F` — are text scans and stay text scans. Keyword and builtin
status is the one genuine question for the interpreter, and it is answered by
**one batched query to bash per run**, which holds the stated ground exactly:
the classification stays a property of bash rather than a roster this tool
maintains. Baking the roster into the crate is refused on that same stated
ground and would drift against the host's own bash; making it consumer config is
refused because a property of the interpreter is not a consumer's to configure.
The query adds no floor — `bash` is already on `GATE_SDK_PROGRAM_FLOOR`, the
crate already spawns it in three production paths, and the arm is reached
through a bash front-end in any case.

**The standing blind spot is carried forward, not discharged.** The scan reads a
member's own declaration text and does not follow a call into a kit library, so
a requirement reached through a shared helper stays invisible. That limit is
`port-blockers-library-mediated-scan`'s and this port neither closes it nor
widens it.

### (6) The default arm's rows and trailer

Criterion 7's roster is emitted from the compiled arm, with the `--needs` read
moving in-process. {design-bearing}

The three positive derivation inputs and the floor filter are unchanged: the
`command -v` guard, command position, and knob resolution for a command-position
expansion, each filtered against the program floor the arm now declares as a
knob. The compiled-member path stops spawning the binary and calls the registry's
requirement lookup directly; the *cannot answer* branch, which the shell reaches
on a non-zero exit, becomes the absent-member branch and keeps its undecidable
row, because a member silently reported clean because the question failed is the
captured-emptiness false green in report form.

The rows and the trailer are byte-identical to the shell arm's, sorted the same
way. No column is added and none is removed: criteria 4, 5 and 6 stay unemitted
on the ground that their only honest reader would have to disregard them.

### (7) The `--group` arm's partition, columns and trailer

Criterion 6's partition is emitted from the compiled arm, with the fixture-dir
resolution shared rather than copied. {design-bearing}

The grouping key stays set-equality over the two derived factors — the
kit-library call set, which is the default arm's own filter inverted, and the
content-glob set read off non-comment lines — with `couples=` printed beside each
member as a cross-check and never fused into the key. The four exclusion classes
and both derived totals, *still owed* and *takeable at this cut*, keep their
grammar. An empty-keyed member keeps its `?` row with its line count and its
declaration path, and empty-keyed members are still never grouped with each
other.

Criterion 2's column must read the same fixture dirs the coverage gate resolves,
so that resolution is extracted to a shared helper rather than duplicated — a
duplicate is a disagreement between the report and the gate about whether a
member carries a pair. **The extracted helper takes its kit roots as a
parameter**: the gate resolves absolute roots, and this report's evidence column
must stay repo-relative, because a report read beside a diff and cited in a
session note carries an absolute clone path that resolves for nobody.

### (8) Byte-identity as the port's parity oracle

Every arm's output is byte-identical to the shell tool's across the port, and
that identity is captured and diffed rather than asserted. {mechanical}

A `bin/` tool takes no fixture pair, so it has no substrate-parity gate; the
oracle available instead is the tool's own determinism over the tree. The port
captures all three arms' stdout, stderr and exit status at the commit before the
deletion, same working directory and same argv, and diffs the compiled arm's
against them. The precedent is this tool's own: an arm has twice been added with
the arms beside it left byte-unchanged, and each time that was run rather than
claimed.

**The expected diff is exactly two lines and is stated ahead of the run** so a
session can tell the port from a regression: `--tree` loses the row for the
deleted file and its trailer moves from `154 file(s) scanned, 12 declared
no-port, 1 temporarily held, 141 owed` to `153 file(s) scanned, 12 declared
no-port, 0 temporarily held, 141 owed`. The owed count — the completion
predicate, and the one number a machine reads — does not move, because the file
was held rather than owed. The two registry arms are expected byte-unchanged.

**What the identity does not cover, stated because it is the port's real
exposure.** Every registered member resolves to a `.gate` descriptor in this
tree, so the tokenizer has no live input here at all: the default arm's rows all
come from the requirement lookup and `--group` excludes every member as already
ported. The byte-identity oracle is therefore empty over precisely the delta 5
code that carries the risk, which is why delta 9 exists.

### (9) The behavioural coverage: the smoke re-pointed, the tokenizer unit-tested

The coverage obligation follows the function into the binary, and the tokenizer
earns compiled tests beside it. {design-bearing}

§The `bin/`-tool contract rules behavioural coverage in place of a fixture pair
on the ground that *the predicate that matters is behavioral* — a ground about
the rule, not about the file's extension — and §The non-gate arm imposes no
coverage obligation that would replace it. So the existing smoke blocks are
**re-pointed at the arm, never deleted**: they cover the front-end path, the
bridged environment and the invocation a caller actually makes, which no
in-crate test reaches. Deleting assertions because their subject moved substrate
is the weakening `check-assertion-strength` exists against, and that gate is
re-armed by this very rewrite.

The tokenizer additionally earns crate tests, because a state machine is tested
far more cheaply and far more exhaustively by unit tests over planted
declarations than by a planted registry, and the crate's test arm runs in the
battery through `check-crate-arms`. The two shapes the smoke pins today — a
here-string, and a `)` closing a command substitution inside double brackets
beside a genuine `case` pattern as the negative control — are carried into those
tests by name rather than left to a rewrite to rediscover.

**Three coverage gaps are recorded rather than silently inherited**, each
structurally absent from the fixture today: the compiled-member requirement path
and its cannot-answer branch, both arms' undecidable counters and the
knob-expansion resolution, and both refusals (non-repository, missing registry).
The port closes the first two in crate tests, where they are one-line
constructions, and leaves the refusals to the smoke where the front-end is.

**One live limit is named and not closed:** this smoke runs at validate and not
in CI, so a port that breaks it is green on the remote oracle. That is the
existing disposition for consumer smoke and this amendment does not move it.

### (11) The name sweep, the consumer's call site, and the retirement

Every surface that names the file is moved, and the file is deleted, in one
commit. {mechanical}

The consumer's measured-claim emitter reads the `--tree` trailer by spawning
bash today and reads the arm instead. It must move **in the same commit**: a
deleted tool leaves the emitter's owed-count parse with nothing to match, the
emitter exits 2, and the consumer's claim oracle fails closed — which §The
non-gate arm recorded as a constraint for exactly this reason. The emitter stays
shell and keeps its `# no-port:` declaration: it is the value of a consumer knob,
it sits in a directory the payload assembler never packs, and its keys are this
project's claim vocabulary, so porting it would put that vocabulary into every
adopter's binary. The trailer's grammar is unchanged, so the parse itself does
not move — only the command in front of it.

The remaining surfaces, each naming the path or the shell invocation: this
repo's always-loaded instruction file; the trajectory's port-sequence section;
gate-sdk's README `bin/` roster, whose entry retires and whose invocation joins
the emit-arm examples beside it — a roster with no gate behind it, which is worth
knowing while editing it; §The port-candidate criteria, §The first cohort, and
the rule that selects the next, §The fourth budget batch, §The twelfth cohort and
§The `# graph:` manifest inside gate-sdk's own SPEC; and one sentence each in
site-kit, canon-kit, evidence-kit and delegation-kit's SPECs — delegation-kit's
being the sharpest, since it cites this file as an example of a runnable artifact
a session invokes by hand, which is the property the port removes.

**No gate catches a missed prose path**, which is why the sweep is enumerated
rather than left to a run: the fenced-invocation gate reaches only fenced repo-
relative paths and this tool is cited in backticks throughout.

Three mechanical consequences ride the same commit: the five generated SPEC and
README mirrors regenerate; the generated hooks and the coupling-graph artifact
regenerate, staged first and regenerated second; and the binary is rebuilt,
which the battery does not discharge.

Two dead permission-allowlist entries in this repo's harness settings name the
deleted script. They are **removals of grants, never additions**, and a settings
file is the user's own surface — the build session raises the removal rather
than taking it silently.

## Producers and consumers

**`--emit-port-blockers` (new interface).** Producer: the new row in the crate's
bridged-arm table, dispatched in `main` ahead of the registry lookup, and absent
from `--list` — the placement §The non-gate arm requires so that the descriptor
set and the `--list` roster stay equal in both directions. Consumers, all three
named and live: this repo's measured-claim emitter, which reads the `--tree`
trailer's owed count; `gate-sdk/smoke/`, which exercises all three arms through
the front-end; and a human session at the cohort-cut transition, which
§The first cohort, and the rule that selects the next names by name as the
instrument that makes its selection rule applicable. Enabling configuration: the
arm's declared knob roster, resolved by `bin/run-gates.sh --emit`, which is the
front-end every other bridged emitter is already reached through — no new
front-end and no new configuration path.

**The union sentinel (new interface).** Producer: the sentinel token in the
arm's declared knob roster, expanded by the crate's knob-roster resolver over
the members of the registry named by the arm's `--gates-dir` argv. Consumer:
the shell bridge, which asks the binary for the roster and resolves each name
before the exec — the same two-step every table member already rides. Enabling
configuration: the `--gates-dir` argument, supplied by the documented
invocations; absent it, the expansion is empty and the arm under-reports.

**The `--gates-dir` argument (new interface).** Producer: the documented
invocations, and the front-end's forwarding of an arm's argv into the
roster request. Consumer: the sentinel expansion and the arm's own registry
walk. It is not a redirect of resolved config — it is the rule's own input, the
gates-dir-positional shape §The non-gate arm's distinguishing test already rules
ports unchanged.

**The disposition triple (new interface).** Producer: the shared header-block
reader plus the well-formedness rule, in the universal layer beside the corpus
rule. Consumers, both named: the `--tree` arm, which prints it as a row's second
column, and the exemption gate's tree half, which reads the held field's slug for
liveness. No third reader is minted.

**No new field is added to any row or any trailer**, which is delta 8's identity
requirement read forward: every column and every count keeps the reader and the
transition it already has, so the every-field-has-a-reader obligation is
discharged by there being no new field.

**Red conditions, because deltas 3, 4 and 11 narrow a corpus.** The narrowing is
one tracked shell file leaving the tree, and it is the tree's only live
`# port-until:` declaration, so the held-field corpus narrows to empty. Each
reader, by what makes it **red**:

- **The exemption gate** reds when a `# port-until:` slug is Done-only or
  missing. An empty field set produces no such slug, so it cannot red; its clean
  line prints the header-field count as a vacuous-pass tripwire, and that count
  going 1 to 0 is a reading, never a verdict. Monotone, and clear by inspection.
  Its queue-side consequence is the *point*: the entry is deferred today
  precisely because a Done move would strand the declaration at a dead slug, and
  the deletion discharges that blocker in the same commit.
- **The substrate-parity gate's assertions G and H** do not widen with the
  fields and never reach a plain script; this file is not a registry member, so
  the narrowing is invisible to them.
- **The consumer's claim gate** reds when its oracle exits non-zero. This is the
  one reader that is **not** clearable by inspection, and delta 11 is the whole
  answer to it.
- **The assertion-strength gate** holds a coverage floor, which the
  causal-completeness rule names as one of the three non-monotone shapes. Delta 9
  re-arms it by rewriting the smoke; it is cleared by running it, never by
  inspection.
- **The install-claim gate** reds on a zero count — the attested case where a
  narrowing *adds* a violation by pruning a declaration's sole instance. Probed:
  the deleted file carries no install declaration, so it holds no instance to
  strand. Verified rather than assumed, because this is the case the rule was
  written from.
- **The comment-tier, shellcheck, exec-bit, deprecation and todo-liveness
  gates** all lose corpus members and red on finding a violation, so a narrowing
  can only remove findings. Monotone.
- **The spec-pointer gate** reds on a pointer naming no section — and, read the
  other way, a section nothing points at. §port-blockers keeps its heading, so
  the arm's crate module must carry the `spec:` pointers the deleted file's
  twenty-seven carried, or the section is orphaned by the deletion. Named here
  because it is the one red the narrowing creates rather than removes.
- **The graph, docs-mirror, enforcement-map and value-rollup freshness gates**
  red on a stale projection. Each is regenerated in the same commit; the hook is
  the sharp one, because its baked values are resolved by running the very
  oracle delta 11 re-points.
