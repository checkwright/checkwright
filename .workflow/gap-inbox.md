VERIFIED FIRST-HAND 2026-08-27 by the iteration lead, independently of the scope session that surfaced it. Two agent worktrees left by scope's survey fan-out carried lock reasons reading 'claude agent <id> (pid 1513285 start 6837434)'. The scope session reported 1513285 was its own parent; the lead probed it separately with ps and found pid 1513285 is the 'claude' process of the LEAD session itself, elapsed 1:10 at the time of reading — i.e. the top-level harness session that dispatched scope, still alive and expected to stay alive for the whole iteration. THE TRAP IS NOT THE STALE LOCK, IT IS THE PID READING GOOD. delegation-kit's own protocol teaches a session to distrust pattern matching and to trust a recorded PID's liveness (the kill -0 loop), so a session meeting a locked worktree does exactly the sanctioned thing, reads a live PID, and concludes the worktree is still in use. It is not: the agent that created it had finished. Under that reading the lock is never clearable from any session other than the creating one, and the iteration-boundary refusal on a linked worktree (lifecycle-kit/SPEC.md bin/enter-stage.sh) is met by a session with no lawful remedy — which is the shape that has previously invited an agent to invent a mutating one. THE ACTUAL REMEDY IS CHEAP AND WAS EXERCISED: git worktree unlock, then remove, then branch -D, no --force needed, after verifying the worktree clean and carrying no commits past the base. Nothing about the lock's pid gates that. NOT FIXED HERE. Candidate shapes, none costed: have the boundary refusal name unlock-remove-branch as its remedy so the message is not a dead end; state in the delegation isolation bullet that a lock reason's pid is the harness's and is not a liveness signal for the agent, since that bullet is where a session learns to reap both halves; or have the reap be asserted at the dispatching session's own turn end rather than at the next boundary, so it lands on the party that can see what the worktree was for. DISTINCT from the reap-both-halves rule already in delegation-kit, which says WHAT to delete and is silent on how to judge whether it is safe to.
