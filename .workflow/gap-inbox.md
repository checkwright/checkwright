- 2026-08-02 — Operator disposition (2026-08-02) on the lossless-compression entry above: Loss is not mechanically detectable -- the gate sees only an entry's current extent, and judging whether a removed line was answered versus dropped is semantic. Therefore the split is authorization-gated: a parent session (e.g. the iteration lead), or the operator in the absence of one, grants permission and issues the recipe for filing a linked task. The recipe must NOT appear in the gate error message. The strong form is intended -- the SPEC states that splitting requires a ruling, and the procedure is issued with the ruling, so a blocked session cannot self-serve. This matches the existing precedent that a check-stage-entry assertion C waiver is written only on an explicit user ruling and never self-issued. The alternative of revising the cap to admit exceptionally valuable content was considered and declined: the gate's own `# spec:` tag states the cap's rationale as "bounded above so it is not an inlined amendment" -- a structural line, not a length preference -- so raising the number moves the number without moving the line, and the entries that would claim the exception are the likeliest ungoverned amendments. A conditional cap also collapses back into authorization anyway, or it is the self-issued exemption the delegation doctrine already names as the standard failure mode. Enforcement-first correction owed with the rule: check-queue-entry-budget's current help text lists lossy compression first ("compress the body to the cap") and then reassures that the narrative "stays recoverable from the evicting commit's own diff". That text is the proximate cause of the measured violation, and its reassurance is half-true in the way already established -- recovery works, signal fails. It must stop blessing compression and instead name the split as authorization-gated, citing queue-kit/SPEC.md section check-queue-entry-budget without inlining the recipe. Untested idea for close to evaluate, not a claim: the gate cannot judge loss, but it may be able to detect the shape of the sanctioned remedy -- a commit that shrinks a deferred entry past some delta while adding no linked entry in the same commit. Not proof, and it will false-positive when a genuinely answered question is deleted, which is exactly the case where the authorization ruling gets cited.
