- 2026-08-23 — read-steer-misses-the-awk-spelling — the bash guard blocks a file read spelled 'sed -n' and a bare 'cat', steering both to the Read tool, and has no clause for awk at all. Measured at this close's prompt-friction triage: 23 of 37 logged awk fall-throughs this iteration are line-range reads of the exact shape awk 'NR>=<a> && NR<=<b>' <file>, doing precisely what the two blocked spellings do and costing an out-of-band permission decision each. Probed rather than assumed: grep over scripts/bash-guard.sh returns no awk match, and guard-kit/lib/guard.sh's two read-steer blocks (the sed one and the bare-cat one) name only their own binaries. Nothing here is a bug — awk was never in the rule's stated scope — but the steer's effect is that a session blocked twice finds the third spelling and reinforces it, which is the opposite of what a steer is for. NOTE the awk case is NOT identical to the other two: awk with a redirect writes, and a large share of legitimate awk use is composition inside a pipe, which the cat rule already exempts by shape. Deliverable is a decision, not a patch: (a) extend the read-steer to a bare 'awk <program> <file>' whose program is a pure NR range, which is the narrowest true predicate and the only one that cannot swallow composition; (b) allowlist 'awk *' and accept awk as the sanctioned composed-read spelling, which masks the steer the other two rules exist to apply; or (c) rule that the steer is spelling-shaped by design and say so in the rule's honest-limit paragraph, so the next triage does not re-file this. Cost while deferred: roughly 23 out-of-band decisions per iteration, and the Read tool's registration-for-Edit benefit is silently forfeited on every one.
