# SPEC amendment: npm-trusted-publishing

Pairs `npm-trusted-publishing`; its observe half is `npm-trusted-publishing-observe`. The publish workflow's `npm` job authenticates with the stored `NPM_TOKEN` secret alone, and a lapsed or emptied token halts the secondary channel after the Release is out. This amendment has the job publish through npm trusted publishing (OIDC), with the stored token kept as the fallback npm reads when no trusted publisher answers. So the set lands, and the next release publishes, whether or not the operator has registered the trusted publisher by close. The observe half reads the first trusted publish and then deletes the secret, which needs no tree change once this lands.

**What the tree and npm do today**, each bullet with the probe or the source that settled it:

- The job writes `~/.npmrc` from `NODE_AUTH_TOKEN`, fed by `secrets.NPM_TOKEN`, and exits 1 when it is empty. It has `id-token: write` and runs `npm publish --provenance --access public "$PWD/${tarballs[0]}"` with no Node provisioning step (`grep -n -A36 '^  npm:' .github/workflows/publish.yml`).
- The runner's npm cannot do OIDC. The job's image, `ubuntu-24.04` at 20261122.23.1 in the v0.44.0 publish run's set-up log, ships Node 22.23.5 and npm 10.9.9 (actions/runner-images, `images/ubuntu/Ubuntu2404-Readme.md`).
- Trusted publishing needs npm CLI 11.5.1 or later, Node 22.14.0 or later, and `id-token: write`. The CLI uses an OIDC credential "before falling back to traditional tokens". Provenance is generated by default for a public package from a public repository on GitHub Actions (docs.npmjs.com, *Trusted publishing for npm packages*).
- The fallback is the CLI's own. `lib/utils/oidc.js` is written never to throw. A successful exchange sets the registry's `_authToken` in the non-persisted `cli` config layer, overriding the `.npmrc` value. A failed one is logged at verbose level and sets nothing, so the `.npmrc` token stands. `lib/commands/publish.js` calls it with the name of the manifest `pacote` reads off a `.tgz` spec, and it passes `enableProvenanceAutoConfiguration: true` (npm/cli, `latest`).
- `actions/setup-node` with `node-version: '24'` provisions an npm that qualifies. Node 24's latest release, v24.22.3, bundles npm 11.19.1, and every 24.x from v24.5.0 bundles 11.5.1 or later. The 22.x line stays on npm 10.9.x (`https://nodejs.org/dist/index.json`). `gates.yml` already pins `actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0` (`grep -n setup-node .github/workflows/gates.yml`).
- The registry records which credential published a version. A trusted-published version's `_npmUser` reads `GitHub Actions <npm-oidc-no-reply@github.com>` (`npm view @npmcli/redact _npmUser`, `npm view @sigstore/sign _npmUser`). `checkwright@0.44.0`'s reads the maintainer account, beside an SLSA v1 provenance attestation (`npm view checkwright@0.44.0 _npmUser dist.attestations.provenance`).
- `package.json`'s `repository.url` must match the repository exactly. `installer/package.json` carries `git+https://github.com/checkwright/checkwright.git`, the form every provenance-signed publish has already passed.
- The token is a granular write token, so npm's 90-day cap reaches it. Classic tokens were revoked on 2025-12-09, and existing granular write tokens were capped at 90 days on 2025-11-05 (GitHub changelog, the npm security updates of 2025-10-10, 2025-11-05 and 2025-12-09; npm's own access-token pages state no cap). The secret was last set at 2026-10-25T14:35:30Z (`gh secret list`), and v0.44.0 published with it on 2026-11-28. So it lapses after 2026-11-28 and no later than 2027-01-23. The exact date is readable only by the operator, at npmjs.com under the account's token settings.
- `check-npm-publish-spec` treats every token after `npm publish` that is not a flag, and not the value of `--access`, `--tag`, `--otp`, `--registry` or `--workspace`, as a positional candidate. It exits 2 on two candidates (`grep -n 'VALUE_FLAGS' native/src/gates/npm_publish_spec.rs`). The publish line does not move here.

## What changes

### (1) The `npm` job runs an npm that exchanges OIDC {mechanical}

**Not yet applied** — `.github/workflows/publish.yml`, the `npm` job. A step `uses: actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0` with `node-version: '24'` runs after the artifact download and before the publish step. It takes no `registry-url`, so it writes no `.npmrc` of its own. The publish step's first command prints `npm --version`, so the run log shows the CLI that published. The permissions block is unchanged: `id-token: write` now carries the trusted-publisher exchange as well as the provenance signature. The `comment-tier-exempt:` line above it says so.

### (2) The stored token is the fallback, never a precondition {design-bearing} {user-facing: a version published by the trusted publisher shows `GitHub Actions` as its npm publisher where it showed the maintainer account; its provenance attestation is unchanged. Settled by the entry's deliverable, npm trusted publishing from GitHub Actions (OIDC), in the unit set the scope recorded 2026-11-28 under the operator's delegation}

**Not yet applied** — `.github/workflows/publish.yml`, the publish step. Where `NODE_AUTH_TOKEN` is non-empty the step writes the `.npmrc` line it writes today. Where it is empty it writes no `.npmrc` and prints one stdout line, `npm: NPM_TOKEN is unset; publishing through the trusted publisher alone`, then continues. The exit 1 and its two-line message go. The `npm publish` line is unchanged, `--provenance` included, so the token path requests provenance by its own flag and not through npm's OIDC-side auto-configuration. A run with neither credential fails at `npm publish` with npm's own authentication error, so the channel still fails loudly rather than publishing unattested. The step's name stays.

Ruled out:

- **`npm install -g npm@<version>` on the runner's Node.** It fetches the publishing CLI from the registry it publishes to, under a version string alone, where the tree already provisions Node through a SHA-pinned action.
- **`node-version: '22'`.** That line bundles npm 10.9.x.
- **A hard npm-version guard.** It would red the secondary channel in exactly the case where the token alone would publish.
- **Dropping the token in this unit.** The set would then land only if the operator registered the trusted publisher by close. Deleting the secret is the observe half's act, after a trusted publish has been read.
- **A verbose-log witness.** The registry's `_npmUser` answers which credential published, free and after the run. `--loglevel verbose`, spelled with a separate value, would also make `check-npm-publish-spec` exit 2 on a second positional candidate.

### (3) The release procedure names the trusted publisher, the fallback and the witness {design-bearing}

**Not yet applied** — RELEASING.md §The procedure, step 5. The sentence "The `npm` job's credential and approval are repository configuration rather than tree state, so a first run on an unconfigured repository fails loudly on the missing token rather than publishing unattested." becomes:

> The `npm` job's credential and approval are configuration outside the tree. The credential is the package's **trusted publisher** on npmjs.com, naming this repository, `publish.yml` and the `npm-publish` environment. The job's npm exchanges the run's OIDC token for it before reading any stored token, so no secret is needed. A stored `NPM_TOKEN` secret, while the repository holds one, is the fallback npm uses when no trusted publisher answers. A run with neither fails loudly at `npm publish` rather than publishing unattested. The registry says which credential published a version: `npm view checkwright@<version> _npmUser` reads `GitHub Actions <npm-oidc-no-reply@github.com>` for the trusted publisher, and the token's account otherwise. Registering the trusted publisher and deleting the secret are the operator's acts, under the operator's npm login, and the local ops runbook carries both as desired state. A new registration expires unless a publish uses it within two days, so it is made within the two days before a tag push.

**Not yet applied, local** — the local ops runbook's desired-state rows. They name the trusted publisher (repository, workflow file, environment) as the publish credential and the `NPM_TOKEN` secret as its fallback, a granular write token under npm's 90-day cap, pending the observe half's deletion. The secret row's "automation token" wording goes, since classic tokens no longer exist. The file is untracked, so no gate reads this edit.

## The operator step

This box's npm holds no login (`npm whoami`, E401), and npm requires account-level 2FA to register a trusted publisher. The lead relays this to the operator. **When:** within the two days before close's tag push, since a registration no publish validates expires after two days. A registration made earlier and lapsed costs nothing but a token-path publish, after which it is deleted and re-made.

- **On npmjs.com:** the `checkwright` package, Settings, Trusted Publisher, GitHub Actions. Organization or user `checkwright`, Repository `checkwright`, Workflow filename `publish.yml`, Environment name `npm-publish`, with publish allowed. Every field is case-sensitive, and npm checks none of them on save.
- **Or by CLI,** npm 11.15.0 or later after `npm login`: `npm trust github checkwright --file publish.yml --repo checkwright/checkwright --env npm-publish --allow-publish`.
- **Not yet:** the package's "disallow tokens" publishing-access setting. It would remove the fallback, so it waits for the observe half's read.

If it is not done by close, the tag's publish runs on the token and the observe half waits for the first release after the registration. *Inferred:* that the token is still valid at close's tag push. Its expiry lies in the bound above, and only the operator's token-settings read narrows it.

## Producers and consumers

- **The OIDC exchange.** Producer: the npm CLI delta 1 provisions, inside `npm publish` on every tag push, enabled by the job's `id-token: write` and by the operator's registration. Consumer: the registry's token exchange for `checkwright`, whose credential npm sets in the `cli` layer for that publish. Unregistered, expired or mismatched, the exchange fails at verbose level and the next consumer is the fallback.
- **The fallback token.** Producer: `secrets.NPM_TOKEN`, while it exists. Consumer: the `.npmrc` line delta 2 writes only when the token is non-empty, which npm reads when no exchange succeeded.
- **The no-token line.** Producer: delta 2, only once the secret is gone. Reader: whoever reads the `npm` job log, first the observe half's next release after the deletion.
- **The `npm --version` line.** Producer: delta 1, on every tag push. Reader: the observe half and close's release watch, confirming the CLI that published was OIDC-capable.
- **The `_npmUser` witness.** Producer: the registry, at publish. Readers: the observe half, which discharges on `GitHub Actions <npm-oidc-no-reply@github.com>` and then deletes the secret, and the release watch of RELEASING.md step 5.
- **The red condition.** `npm publish` with neither credential answering fails, and so does the `npm` job. That is the red step 5's watch already reads: fixed, and the tag re-pushed.
- **Gates whose corpus is `.github/workflows/`** (`git grep -l 'workflows' -- '*.gate'`, read hit by hit), plus the action pin and permission gates. `check-npm-publish-spec` still counts one invocation with an unchanged spec, since the publish line does not move. `check-action-pinning` reads the new `uses:`, which carries a full SHA. `check-action-permissions` reads an unchanged block. `check-gate-substrate-parity` assertion F reads no new digest emission. `check-release-assets`, `check-release-channel-parity` and `check-value-rollup-fresh` read steps this amendment does not touch. `check-comment-tier` reads the rewritten `comment-tier-exempt:` line.
